# Delivery review: ToolkIT, 2026-10-12

Reviewer: a fresh Claude session with no memory of building the app, acting as a skeptical senior
engineer. Read: README.md, ARCHITECTURE.md, ENGINEERING-STANDARDS.md, all of `app/`, `tests/`,
`tools/build_release.py`, the launchers, GETTING-STARTED.html and the git history. Ran (read-only):
`pytest` (416 passed, Python 3.12), `ruff check .`, `ruff format --check .`, `mypy` (all clean), and
throwaway probes with FastAPI's test client against temporary folders (outside the repo). Nothing
in the repo was changed except this file.

Verdict: APPROVE AFTER FIXES: the tools are correct, well tested and safe by design, but two
failure paths around the OUI files break the app silently, and one of them is triggered by
following the README's own recovery step.

Minimum to fix first:
- Finding 1 (one problem with the OUI files makes every tab fail).
- Finding 2 (a failed save during Update/Import gives a blank 500 and can leave mixed files).
- Finding 3 is a five-minute fix; worth doing in the same pass.

## Findings (most severe first)

1. [important] `app/web/templating.py:65`, `app/web/oui_state.py:48-60`: any problem with the files
   in `data/oui/` takes down **every** tab, not just the OUI lookup.
   `render()` calls `oui.status()` on every response, including the small htmx result blocks for
   unrelated tools. `status()` and `reload()` have no error handling, so:
   - deleting `data/oui/` while the app runs (exactly the README's "Recover" step, README.md
     line 186) makes `min(dates)` fail on an empty list: verified, `GET /` and `POST /vlan` both
     return 500 until the app is restarted;
   - an unreadable or invalid file in `data/oui/` (a hand-copied wrong file, a locked file, a
     future parser that's stricter than the one that saved it) raises `OUIDataError` /
     `OSError` / `UnicodeDecodeError` on every request: verified, every page returns 500.
   Why it matters to the client: the subnet calculator stops working because of a vendor-list
   file it never uses, the error is a bare "Internal Server Error" that points nowhere near the
   cause, and the documented fix makes it worse unless the app is restarted.
   Suggested fix: make the OUI state fail soft. Catch file errors in `reload()` and keep them as a
   "the list couldn't be read: <reason>; click Update or Import" status instead of raising;
   in `status()`, treat "no dates" as "no list". Only compute `oui_status` for the full page
   (`index.html`) and the OUI routes, not for every result fragment. Add tests: a corrupt
   `oui.csv`, and the folder deleted after the first load, each still serving `GET /` and
   `POST /vlan`. Say "stop the app first" (or nothing, once it's fixed) in the README's Recover line.

2. [important] `app/tools/oui_update.py:92-93` and `:131-147`, `app/web/routes/oui.py:144-170`:
   a save that fails (read-only or full disk, a folder the user can't write to, antivirus holding
   the file on Windows) raises a plain `OSError`, which the routes don't catch.
   Verified with a read-only `data/oui/`: `POST /oui/update` returns 500. With htmx, a 500 isn't
   swapped in, so the user clicks Update, the button greys out, and then nothing happens. Also,
   the three files are saved one after another: if the second save fails, `oui.csv` is new and the
   others are old. README line 187 says a failed Update "never damages the existing list (files are
   checked first, then swapped in whole)": true for downloads, not for saves.
   Why it matters to the client: the one feature that touches the disk and the network fails with
   no message, in a situation (a locked-down laptop, a folder in a protected place) that's
   realistic for colleagues.
   Suggested fix: in `_save()` (or around the save loop), turn `OSError` into `OUIUpdateError` with
   a message that names the folder and the reason ("couldn't save to ...\\data\\oui: permission
   denied"). Reword the README line to "each file is replaced whole; a failed download changes
   nothing". Add a test with a fetcher that succeeds and a folder that can't be written.

3. [minor] `app/web/forms.py:32-34`, `app/tools/vlan_list.py:69-70`: a number longer than 4,300
   digits crashes the route with a 500.
   Python refuses to convert digit strings that long to `int` (a safety limit since 3.11) and
   raises a plain `ValueError`, which the routes don't catch (they catch `FormError` /
   `VLANListError`, which are subclasses, not the parent). Verified: `/ip` and `/mac` with such a
   count, and `/vlan` with such a "VLAN", return 500. `/subnet` and `/iplist` are safe because
   their patterns cap the digits.
   Why it matters to the client: unlikely to be typed by hand, but a mis-paste into a big textarea
   can do it, and the result is again a silent no-op instead of the "clear refusal" the docs
   promise.
   Suggested fix: cap the digits before converting (e.g. more than 6 digits in a count is "too
   large"; `_ITEM` could be `(\d{1,5})(?:-(\d{1,5}))?` so longer numbers are reported as
   "not a VLAN"). One test per route.

4. [minor] No safety net for unexpected errors (all htmx forms).
   Findings 1-3 share one effect: any exception the code didn't foresee gives a 500, which htmx
   silently ignores, so the page looks frozen. The architecture handles *expected* errors well
   (each tool's own error class, shown with HTTP 200); there's nothing for the unexpected ones.
   Why it matters to the client: the next unforeseen bug will also look like "the button does
   nothing", which is the hardest kind of report to act on.
   Suggested fix: one small thing, either an exception handler in `create_app()` that returns a
   friendly result block ("Something went wrong: <type>. Details are in the console window.")
   for htmx requests, or a few lines in `app.js` listening for htmx's `htmx:responseError` event
   and showing a message in the target. Not both.

5. [minor] `app/tools/subnet_calc.py:213-220` (used by IP list cleanup too): the two ambiguous
   masks are always read as /32.
   `0.0.0.0` (as a mask, Cisco's "default route / any") and `255.255.255.255` (as an ACL wildcard,
   "any") both become a single host. The code's docstring explains this choice, and it's a
   reasonable one, but it isn't in the README's Known limitations or the page hints. In IP list
   cleanup, a pasted ACL line meaning "any" silently becomes one host, and the summary is then
   wrong for that ACL.
   Why it matters to the client: the tool is advertised for ACLs; "any" turning into one address
   is the kind of quiet surprise that ends up in a config.
   Suggested fix: at minimum, add it to Known limitations and the two tabs' hints. Better: when
   either value is used as the size, add a warning line ("read 0.0.0.0 as a wildcard: one host; if
   you meant 'any', use 0.0.0.0/0").

6. [minor] `app/tools/hostname_faker.py:57` and `:228-234`: letters outside A-Z pass through
   unchanged.
   Anything that isn't an ASCII letter or digit counts as a separator and is copied as-is, so a name
   with an accented letter keeps that letter in the same place (verified: in a name like
   `zürich-sw01`, the `ü` survives into the fake). Separately, `str.lower()` can change a
   string's length for a few Unicode letters, which would misalign `_apply_case()`'s
   character-by-character copy.
   Why it matters to the client: this is the privacy tool; its one job is not to leak real names.
   Hostnames are almost always ASCII, so the risk is small, but it's undocumented.
   Suggested fix: either report lines that contain non-ASCII characters (simplest, consistent with
   "report, don't guess"), or add a line to Known limitations. Not worth a Unicode-aware rewrite.

7. [minor] `app/web/routes/ip.py:43`: the router re-parses the raw text to decide whether to say
   "rounded down from ...".
   It splits the user's text by `/` and spaces to rebuild the address, repeating part of
   `parse_target()`'s job in a different way. I found no input where it's wrong today (the
   `ipaddress` module rejects the odd ones first), but it's the "same rule written twice" red flag
   from the standards.
   Why it matters to the client: the two copies will drift the first time `parse_target()` learns a
   new input form.
   Suggested fix: have the tool say it (e.g. `IPResult.host_bits_cleared: bool`, or compare
   against an `IPv4Interface`), and the route only words it.

8. [minor] Documents and comments that don't match the code:
   - README line 203 and ARCHITECTURE "Rules" say at most 65,534 items per request "in every tool".
     The VLAN list has no item limit (harmless: 2 million junk items took ~1 s), and the subnet
     split limit is 65,536 subnets. Say which tools have which limit.
   - README line 186 "Recover": see finding 1 (needs "stop the app first" until that's fixed).
   - README line 187: see finding 2.
   - `run.bat:12` points to "Quick start" in README.md: the section is called "Getting started",
     and README.md isn't in the release zip, so a colleague who sees this message can't follow it.
     Point to GETTING-STARTED.html, which is shipped.
   - `app/settings.py:28-30` says `data/` "ships empty in a release"; the decision (and
     `tools/build_release.py`) is that it isn't shipped at all.
   - `app/web/routes/pages.py:2` says "four tabs" (there are eight); `app/web/responses.py:51`
     says `Table` is for the OUI tab (the subnet split uses it too).
   Why it matters to the client: each one is small, but a reviewer who finds two stale comments
   stops trusting the rest of the comments, and this codebase leans on its comments heavily.
   Suggested fix: one pass over the list above.

9. [minor] Tests: a few important behaviours aren't tested.
   - Security middleware: the Referer fallback (no Origin, foreign Referer) and `Origin: null`
     are untested (both behave correctly today: verified `Origin: null` gets 403). The
     `__main__.py` refusal to start on a non-local HOST is untested.
   - OUI state: no test for a corrupt, unreadable or vanished file (finding 1), or a failed save
     (finding 2).
   - Very long numbers (finding 3).
   The existing tests are good: they assert real outcomes (exact output lines, file names, CRLF
   counts, 403s), use fake fixtures only, seed the random generators, and inject a fake fetcher so
   nothing touches the network. No test I read was hollow.
   Why it matters to the client: the untested paths are exactly where findings 1-3 were.
   Suggested fix: add the tests alongside fixes 1-3, plus two middleware tests.

10. [minor] `requirements.txt`: runtime packages are lower bounds only (`fastapi>=0.115`, ...).
    The release zip bundles whatever was installed into `python/` on the day it was prepared. If
    `python/` is rebuilt later, a new major version (Starlette has already moved to 1.x, per
    `requirements-dev.txt`) could change behaviour with no change in the repo.
    Why it matters to the client: two release zips built from the same commit could behave
    differently, and nobody could tell which versions a colleague has.
    Suggested fix: pin the versions that were tested on the laptop (`fastapi==...`), or keep a
    `requirements.lock` from `pip freeze` of `python/` and build from that. Upgrades become a
    deliberate step, as already done for ruff.

### Verdict on the departures listed in ARCHITECTURE.md

ARCHITECTURE.md asks this review to decide on its recorded departures. My view:

- **Folder names (`web/routes`, `tools`, `settings.py`):** accept as a documented decision. The
  separation is real (verified: nothing in `app/tools/` imports FastAPI, Starlette or `app.web`).
  Renaming would be churn with no behaviour gain. Turn the "recorded, not yet decided" Decision
  into a decided one.
- **No `repositories/` folder:** accept, with one note: `oui_data.load_folder()` and
  `oui_update.file_dates()` are the disk code; if the OUI state is reworked for finding 1, that's
  the natural moment to put the file access in one place (e.g. all of it in `oui_update.py`,
  renamed `oui_files.py`), so "where is the disk touched?" has a one-file answer.
- **Plain constants instead of pydantic-settings:** accept. Nothing is user-configurable, and
  adding a settings class would be a moving part with no user (principle 9).
- **No `schemas/`:** accept. Dataclasses beside their code are fine at this size.
- **Long route handlers:** mostly accept. They're presentation (wording summaries). Two
  exceptions worth moving into the tools, because they're rules, not wording: the "mostly single
  addresses" test in `routes/iplist.py:54-55`, and the host-bits check in `routes/ip.py:43`
  (finding 7).
- **One limit, several copies (65,534 in five places, `MAX_TABLE_ROWS` in two):** fix; it's cheap.
  One `MAX_ITEMS` constant (in `settings.py`, or a tiny `app/tools/limits.py` if the tools
  shouldn't import settings), and `MAX_CONVERT_LINES` renamed, since the OUI lookup uses it too.

### What's good (so the fixes are kept in proportion)

- The tools are pure, small, heavily commented and well tested (416 tests, ~5 s), with careful
  edge cases: /31 and /32, host bits, mask vs wildcard by shape, CRLF downloads, blank-line
  alignment for spreadsheet columns.
- Security is right for a local tool: 127.0.0.1 only (checked twice), Host check against DNS
  rebinding, Origin/Referer check against CSRF, fixed download file names, auto-escaping, and the
  one `Markup()` escapes each item first. No credentials anywhere.
- Input limits are real for the tools that need them; Update/Import read with size caps;
  downloads are validated before saving; the network code is injectable and never used by tests.
- The repository and its history are clean: one commit identity (the noreply address), no 10.x
  values, none of the strings the pre-publish audit targeted, fixtures invented, the private
  notes files never committed.
- Nothing is over-engineered: no database, no JS framework, no build step, two runtime
  dependencies beyond FastAPI's own. The hostname faker's "deck" is the most complex piece and its
  complexity is justified and explained.
- README, runbook, Known limitations and GETTING-STARTED.html exist and are mostly accurate (the
  exceptions are in finding 8).

## Compared with the author's weak spots

Written after my findings above, from HANDOFF.md "Known weak spots" (10 items).

**Author's weak spots I also found:** 1 (layer names and placement), 2 (one limit in five places),
3 (long route handlers): see "Verdict on the departures". 5 (Update's save isn't all-or-nothing):
part of finding 2, which adds that the failure also shows as a silent 500. 10 (coverage not
measured): consistent with finding 9, where the untested paths are exactly where the bugs were.

**Author's weak spots I missed or didn't check:**
- 4 (Import upload spooled to disk with no size cap): I read past it. I agree with the author's
  reading of Starlette (the per-part limit only applies to text fields) and with "low risk": the
  only person who can upload is the user on their own machine. Document it as a known limitation;
  not worth code.
- 6 (a POST with no Origin and no Referer is allowed): I looked at it and accept it. Current
  browsers send Origin on every cross-site POST, so a web page can't produce a header-less POST;
  the allowance only serves local tools like curl. Keep it, as recorded in ARCHITECTURE.md.
- 7 (not run on Python 3.14 since the ruff/mypy commits): not checked; I only ran 3.12. Those
  commits touched app code, so this must be done before the gate, as HANDOFF already says.
- 8 (release zip never built or run on Windows; GETTING-STARTED not re-followed): not checkable
  from here. I read GETTING-STARTED.html against the templates and found it accurate, but that
  isn't a substitute for extracting the zip on the laptop.
- 9 (`pydantic` listed but never imported): noticed, not listed. Trivial: keeping it as an explicit
  dependency is fine; it belongs with the pinning in finding 10.

**Problems I found that the author didn't list:**
- Finding 1: one OUI file problem (including the README's own recovery step while the app runs)
  makes every tab return 500. The most important finding in this review.
- Finding 2 (the part beyond weak spot 5): a failed save is an unhandled `OSError`, shown as
  nothing at all.
- Finding 3: numbers over 4,300 digits crash `/ip`, `/mac` and `/vlan`.
- Finding 4: no safety net for unexpected errors under htmx.
- Finding 5: `0.0.0.0` / `255.255.255.255` always read as /32, including "any" in ACL lines.
- Finding 6: the hostname faker passes non-ASCII letters through.
- Finding 7: the router re-parses the IP generator's input.
- Finding 8: stale documents and comments (limits wording, Recover step, run.bat, settings.py,
  pages.py, responses.py).
- Finding 10: runtime dependencies aren't pinned, so release builds aren't reproducible.

**Overall:** the author's list is honest and accurate about *structure*. It's weaker on *runtime
failure paths*: none of its items is "what happens when something goes wrong while the app is
running", which is where findings 1-4 are. A useful habit for the next project: for every file,
network call or user number, ask "what does the user see if this fails?" and test that answer.
